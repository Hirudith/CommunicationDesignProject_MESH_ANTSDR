# r6.1 failure report

Every failure observed on the ANT-SDR E200s with r6.0.1 (section 2 of the
task, plus the console log and screenshots sent during the work), traced
through root cause, fix, regression test and measured result.

**What "measured" means here.** Nothing in this report was measured on the
E200s. The evidence comes from four places, named in every row:

- **sim** — `bpsk_meshsim.py` with its r6.1 radio model (self-coupling, 12-bit
  ADC with clipping and RX gain, IQ image placed by each version's own
  channel plan, ACLR, SINR-based decoding, transmit and receive latency);
- **blocks** — GNU Radio 3.10.9 running the r6.0.1 blocks and the r6.1 blocks
  side by side on the same synthetic samples (`test_grc.py`);
- **flowgraph** — the complete generated r6.1 flowgraph on recorded samples,
  the Pluto blocks replaced by a paced file (`dev/grc_rx_check.py`,
  `dev/cpu_check.py`);
- **bench** — `bpsk_zmq_bench.py`: 2–4 complete node processes, each running
  the generated flowgraph with the Pluto blocks replaced by DAC/ADC models
  (gain, 12-bit quantisation and clipping, IQ imbalance, ±ppm clocks, buffer
  latency, faults) and a shared ZMQ "air", slowed down 8–32× to fit a 2-core
  machine. Timing on the bench is S× slower than on the radios.

Every `test_r61` check named below fails on r6.0.1 and passes on r6.1
(`BPSK_TREE=<r6.0.1 tree> python3 test_r61.py`; both outputs are in
`dev/results/`). `test_grc` runs the r6.0.1 blocks next to the r6.1 ones and
reports both.

## F1 — Mirror-image self-interference

**Seen.** A on channel 0 (−900 kHz), B on channel 3 (+900 kHz): A heard B at
−2 dB SNR with 21 % frame errors; the handshake never completed.

**Root cause.** The r6.0 plan was two-sided (−900/−300/+300/+900 kHz) and the
AD9361's IQ imbalance leaves an image at −40…−50 dBc on the mirror frequency.
Channel k's image fell exactly on channel 3−k. A node's *own* transmitter
(20–40 dB above any neighbour at its own ADC) therefore put an image 0–25 dB
above the neighbour on the mirror channel.

**Fix.** One-sided plan at 6 MS/s: +450, +1050, +1650, +2250 kHz. Every image
lands at a negative frequency, where there is no channel; DC/LO leakage is
281 kHz outside channel 0; the band edge is at 81 % of fs/2.

**Tests.** `test_r61` F1a (the plan the node block actually uses: r6.0.1
offsets −900…+900 kHz, image hits 0↔3, 1↔2; r6.1 none), F1b (sim: two
nodes on channels 0 and 3 — r6.0.1 SINR −20 dB both ways, no session; r6.1
session in 1.1 s, 29.8 dB both ways, messages delivered); `test_phy` plan
checks; `test_grc` G6 (flowgraph: own TX on channel 0 at −8 dBFS with a
−45 dBc image, nothing decoded on channel 3, both neighbours decoded).

**Measured.** flowgraph: neighbours on channels 1 and 2 decoded 302/307 and
303/308 (the missing frames are inside a deliberate 40 ms gap) with the own
transmitter and its image present.

## F2 — Own transmitter overloads own receiver

**Seen.** One direction 29 dB, the other nothing; later 0.4 dB; the deaf node
recovered when its TX attenuation was raised. Node A's console: "receiver
overloaded: 61.8 % / 37.7 % of ADC samples at full scale" at tx_atten 50,
rx_gain 30. Node B's screen: SNR −5.5 dB, FER 11.3 %, 2619 CRC fails.

**Root cause.** Two, compounding. (1) The own signal sits inside the receive
band and reaches the ADC unfiltered; with fixed gains it clipped, and
clipping distortion buries the neighbours. (2) Even unclipped, r6.0.1 could
not decode a weak neighbour: it had no AGC, and the FLL, symbol-sync and
Costas loop gains all scale with the signal amplitude. Measured (blocks,
r6.0.1 chain as generated): a neighbour at −10 dBFS decodes, at −30 dBFS and
below **nothing decodes** — and a neighbour must sit 20–40 dB below the own
signal, which itself must stay below full scale.

**Fix.** Closed-loop gain staging (`bpsk_gain.py`: RX gain holds the ADC peak
in −20…−9 dBFS, never above −6; TX attenuation holds every neighbour near
15 dB; hysteresis, rate limits, bounds, manual override; README *Control
laws*). The own channel's signal is removed from the others by the 65 dB
channel filters. A per-channel AGC (`agc3_cc`, attack 1.0 — bounded output,
see R1 below) normalises every channel before the loops.

**Tests.** `test_r61` F2 (sim, own signal clipping the ADC: r6.0.1 70 %
clipped, SINR −15.9 / −36.8 dB, nothing delivered; r6.1 0 % clipped after
the loop settles, 25 / 20 dB, delivered), `test_phy` gain-law checks (13),
`test_grc` G7 (blocks, +18 kHz offset: −10 / −40 / −55 dBFS → r6.0.1 78 / 0 /
0 of 79 frames, r6.1 78 / 78 / 78), G5 (r6.1 chain: silence, a transmitter at
−1 dBFS switching on, then one at −55 dBFS: all decoded).

**Measured.** bench: every node starts at 30/50 dB, clips on its own carrier
(4–6 % of samples at full scale), drops RX gain to 6–18 dB within a second,
then settles with 0 % clipped and the ADC peak at −9…−20 dBFS: two nodes at
RX 22–26 dB / TX attenuation 62–65 dB, hearing each other at 21–23 dB; four
nodes (1/32 speed) at RX 8–17 dB / TX 46–50 dB, all 12 links at 22–29 dB.

## F3 — Receiver freeze on a corrupted header

**Seen.** `sched: <block repack_bits_bb> is requesting more input data than we
can provide`, `ninput_items_required = 98408`; one stalled branch froze all
four channels and the source. With r6.0.1's 1 MiB buffers a bogus header
still stalled a channel for ~2 s.

**Root cause.** A DBPSK symbol error flips two adjacent bits, so both copies
of the 16-bit length field change identically and still agree: 13 → 0x300D
= 12301 bytes = 98408 bits. GNU Radio **3.10.12** reads all 16 bits
(`payload_length() = (hdr >> 16) & 0xffff`; 3.10.9 masked to 12 bits, which
is why the bug is version-dependent). `repack_bits_bb` then waits for 98408
bits — more than its buffer, a freeze; with bigger buffers, it swallows every
frame in the next 98408 bits instead.

**Fix.** A numpy deframer (`bpsk_phy.Deframer`) in the flowgraph's embedded
blocks: lengths outside 13…600 bytes are rejected at once, the copies must
agree, the search for access codes continues *inside* a frame being
collected (so a plausible-but-wrong length costs only that frame), and it
never waits for data it does not have. `bpsk_link` refuses to build any frame
over 600 bytes (fragments are ≤ 304).

**Tests.** `test_r61` F3, `test_phy` (8 deframer checks: 12301-byte header,
500-byte wrong length, mismatching copies, 2/3 code errors, random bits,
throughput 34 Mbit/s per core), `test_grc` G4 (blocks: r6.0.1 chain loses
15 of 30 following frames — 3085-byte corruption, as 3.10.9 masks the high
bits; r6.1 loses none), G6 (flowgraph: corrupted header mid-stream, 0 frames
lost around it).

**Measured.** bench, 3 % of one node's frames with corrupted lengths: 15
headers rejected at each receiver, 14/14 messages, FER 0, no fault.

## F4 — Overflows and process termination

**Seen.** `OOOO…`, "no tick from the Message Strobe", the process ended.

**Root cause.** The node block read the four symbol streams and the ADC as
stream inputs. Each symbol stream runs on its own transmitter's crystal, so
a block reading them together throttles the fastest to the slowest; the
backlog reached the radio source, which overflowed. r6.0.1 fixed the lockstep
consumption but still ran per-sample Python on five streams.

**Fix.** The node block has **no stream ports**. It receives C++-cut
snapshots as PDUs (`keep_m_in_n → stream_to_tagged_stream →
tagged_stream_to_pdu`): 512 symbols per channel every 0.1 s (EVM/SNR,
constellation), 4096 channel samples every 0.1 s (level, AFC), 8192 radio
samples every 50 ms (ADC peak/clipping, spectrum). Decoded bits reach the
deframers in 8192-bit vectors (33 ms per Python call). No block mixes streams
of different receive channels. gr-iio's `O`/`U` are counted from stderr and
shown (tile, Radio pane, log, CSV).

**Tests.** `test_r61` F4a (r6.0.1: 5 stream inputs), F4b (r6.0.1: the node
block reads ch0…ch3), `test_shim` (no stream ports, every handler a named
method).

**Measured.** bench: 0 overflows after warm-up in every run (2 nodes ±25 ppm
300 s; 4 nodes 300 s; fault runs; the long runs below). The counter itself
was verified by injecting buffer drops (and fixed on the way: only the first
`O` of a run was counted).

## F5 — Lag and persistent one-way link

**Seen.** Laggy console and Qt plots; "node A doesn't hear you"; node B:
own echo 4.6 s / 7238 ms ("host too slow"), "securing link…", "radio process
not reachable – reconnecting…".

**Root causes and fixes.**

| Cause | Fix | Test (r6.0.1 → r6.1) |
|---|---|---|
| The carrier was kept up with IDLE frames back to back: ~200 frames/s per channel, each decoded in Python by every receiver | PRBS-15 filler between frames (no 64-bit window within 15 bits of the access code); IDLE only as a 0.5 s keep-alive | F5a: 195 → 2 frames/s |
| ACK and handshake timers fixed (0.5 s / 1 s) while the echo was 4.6 s: every frame retransmitted, handshake retries replaced each other before any answer arrived | ACK wait + 2 × measured echo; handshake retry ≥ 2 × round trip, cap raised past it; static nodes measure the echo from their keep-alives | F5b (sim, 2.5 s receive latency, 3 nodes): no session / failed → all sessions, all delivered |
| Crossed handshakes on a slow link left each node's current session paired with the other's previous one; both dropped every frame as "unknown session" until the 10-min rekey | a node that keeps receiving frames for a session it does not hold re-keys (the lower address wins a crossing); the wait for a confirmation follows the round trip | F5d (scripted, 1.7 s each way): 0 → 30 frames opened in the last 30 s |
| A one-way link was treated as a collision: the node hopped channels | silence check first; clear channel → link fault, reported with the reason, no move; the UI shows *can't hear you* + reason | F5c (sim, a node nobody can decode): 2 moves, no fault → 0 moves, LINK FAULT, *can't hear you* |
| The UI showed only "doesn't hear you" | two-way SNR table in beacons and in the Links pane; states not approved / can't hear you / no response / securing | `test_r61` W2–W5, `test_shim` |
| (found while measuring) the UI event backlog kept 2000 snapshots (stats, constellations, spectra): memory grew ~300–500 MB/h until it filled | snapshot events replace their predecessor | flowgraph: flat after warm-up |

"Radio process not reachable": the page's event stream starved while the
Python side was saturated. r6.1 cut the Python per-frame work (above) and the
node block's share is 0.17–0.19 core at the full 6 MS/s (flowgraph measurement),
and the page of a bench node checked in a browser during a run was live and
current. Not measured on the user's laptops.

## F6 — CPU load

**Seen.** r6.0.1 at 3 MS/s: RX ≈ 1.5 cores (FLLs ≈ 0.54), TX ≈ 0.5; each
offscreen Qt sink 0.1–0.15; a 6 MS/s one-sided prototype RX 2.2 / TX 1.5.

**Fix.** FLLs replaced by the AFC (a 4096-point FFT per channel 10×/s in
Python + one rotator); channel filters `freq_xlating` (decimate first); TX
interpolates straight to the radio rate with one polyphase RRC (no rational
resampler); Qt sinks fed 1 sample in 16 (constellations) or 1024 in 61440
(spectra) by C++ `keep_m_in_n`; no per-sample Python anywhere.

**Tests.** `test_r61` F6 (r6.0.1: 4 FLLs, 6 undecimated Qt sinks).

**Measured.** flowgraph, this machine (Xeon, 2 vCPUs), the whole process with
Pluto-sized buffers, the paced file source and null sink that stand in for
the radio (0.19 core at 6 MS/s, 0.09 at 3 MS/s) subtracted: **r6.1 1.42
cores at 6 MS/s** (DSP blocks and deframers 1.25, node block 0.17; an
earlier run gave 1.52); **r6.0.1 1.80 cores at 3 MS/s** (FLLs 0.56, TX
resampler 0.28, node block 0.19). Per-thread breakdowns in
`dev/results/cpu_r6.1.txt` and `cpu_r6.0.1.txt`. On the E200's host laptops
the absolute numbers will differ; the ratio should not. On the bench (1/32
speed) each node process used 0.27 core on average over the 2-hour soak.

## Long runs on the bench

Four nodes, ±25/±20 ppm crystals, 1/32 speed (every node therefore a "slow
host": ~3 s echo, a level reading every 3.2 s), traffic every few seconds.

| Run | Code | Result |
|---|---|---|
| first soak, 111 min (the workspace was restarted at 111 of 120 min) | before the fixes below | 0 overflows / underflows on all nodes; all 12 links 23–30 dB, FER 0; memory 156 → 160 MB per node, growth slowing (~3 MB/h first hour, ~1 MB/h second; the Python heap is ~2 MB, tracemalloc); found: two nodes sharing a channel for 10 min after start-up, the RX-gain limit cycle, the bench's TX-queue scaling (rows above) |
| second, stopped at 15 min | + those fixes | found the one-second *can't hear you* blips (row above) |
| third, stopped at 5 min | + the blip fix | found two pairs of nodes stuck on shared channels, reporting link faults (row above) |
| two short runs (5 and 11 min) | intermediate versions of that fix, both rejected | one mistook the own signal's tail for a second node at start-up; one made every check wait for level readings, which at 1/32 speed meant ~8 s silences and neighbours showing each other *away* |
| fourth soak, 27 min (the workspace was restarted again) | as shipped, except the last two start-up fixes (own level follows the RX gain; nodes that hear nobody) | 0 overflows / underflows; all four on separate channels after one start-up collision, 0 moves after that; all 12 links 22–29 dB, FER 0; every link `ok` every second after the first 5 minutes (one second of `away`); 0 transmit-queue drops; memory +1–2 MB |
| **2-hour soak** | **as shipped** | 2 h complete: 0 overflows / underflows on all nodes; two start-up collisions resolved within the first minute, 0 channel moves after that; all 12 links 20–29.5 dB, FER 0, every link `ok` every second after the first 2 minutes except one second of `away`; 1163/1163 group messages delivered with all receipts; 0 transmit-queue drops; 0.27 core per node; memory 157 → 160–161 MB per node (1.5–2 MB/h; the Python heap is ~2 MB) |

Memory is not perfectly flat: each node process grew by 3–4 MB over the two
hours (157 → 161 MB), at a rate that fell during the earlier 111-minute run
(~3 MB/h in the first hour, ~1 MB/h in the second). The Python heap stays
around 2 MB (tracemalloc), so the growth is in the native side (GNU Radio,
numpy, Qt, the allocator); r6.0.1 grew by 444 MB/h in the same harness. The
2-node and fault runs in the README were repeated on the code as shipped.

## Not verified on hardware

All of it. In particular:

- the AD9361/E200 itself: real self-coupling and IQ-image levels, LO
  leakage, the gain table behind `hardwaregain`, analog TX regrowth, and the
  ADC behaviour under overload — the models are generic;
- that gr-iio's IIO Attribute Sinks accept `hardwaregain` and `rf_bandwidth`
  on `ad9361-phy`/`voltage0` as used (they throw on a refused write; the gain
  law stays within the documented ranges), and what gr-iio does after the
  USB/Ethernet link drops and returns;
- GNU Radio **3.10.12** and Python 3.14: the flowgraph was generated and run
  with 3.10.9 / Python 3.12; the `.py` was adjusted to the 3.10.12 layout and
  uses no API that differs between the two, but it has not been run there;
- CPU and responsiveness on the lab laptops (measured on a 2-vCPU cloud Xeon);
- the acceptance numbers themselves — SNR ≥ 15 dB both ways, FER < 1 %,
  session < 2 s after mutual Trust, 12 links ≥ 12 dB, 3/3 receipts for 10 min,
  0 channel moves and 0 overflows over 30 min — were met on the bench and in
  simulation, at the bench's slowed-down timing; they need the checklist in
  the README run on the radios.
